# 原生待发送队列

## Native pending-message queue (desktop experimental contract)

`nativeQueue:true` advertises queue.list/add/update/delete/reorder only for exact DesktopBaseline 0.163.0-alpha.10.2. The five experimental Params/Response pairs are exported by that binary, separately fingerprinted in queue-lock.json, verified by build.rs and schema.mjs, and unavailable to Managed 0.159.2. No production schema was edited and the default runtime version is unchanged.

All actions require sessionId. add requires text, update requires submissionId and text, delete requires submissionId, reorder requires unique submissionIds in full current membership order. list returns `{sessionId,upstreamThreadId,data:[<native QueuedSubmission>]}`; mutations return `{sessionId,upstreamThreadId,result:<validated native result>}`. No native thread/path override is accepted. Source identity, exact cwd grant, tombstone and RPC generation are checked before/after calls. Lists aggregate bounded pages (up to 128 entries / 384 KiB); mutation request IDs use the existing per-device durable deduplication journal. Add uses a stable device/request-derived native clientUserMessageId. Unknown mutation outcomes require refresh, never automatic resend.

The authority owns all pending entries and their persistence; Bridge does not maintain a second queue. Update/delete validate native membership; text update is rejected for entries containing non-text input to avoid discarding attachments. Reorder rejects changed membership; no upstream atomic revision contract exists, so concurrent edits are not claimed conflict-free. Native queue notifications and automatic Android refresh remain pending; the viewer explicitly refreshes. Android exposes enqueue for running conversations, and a separate viewer to inspect/edit/delete/move pending entries. It clears composer drafts only after native acceptance. This batch does not expose thread/queue/start or implement a Bridge scheduler: execution-policy/lifecycle and original-desktop dispatch remain to be verified. Native queue CRUD is not evidence of full automatic queue behavior or desktop parity.

## Explicit native queue start and invalidation events

`nativeQueueStart:true` adds queue.start with exactly `{sessionId,submissionId}` under the selected DesktopBaseline profile. ThreadQueueStartParams/Response are captured by the exact locked binary in a separate queue-start-lock.json, verified by Rust build and schema.mjs. Existing queue operations remain unchanged. The request is included in the durable device mutation journal, and unknown outcomes must never be automatically resubmitted.

Start requires a verified boundary, no local active/unreconciled turn, fresh authoritative idle state, no active Goal, concurrency availability and a live unchanged grant/thread/runtime. Because the native queue/start method has no per-turn policy overrides, Bridge explicitly resumes the original thread with workspace approval defaults and validates the returned cwd and sandbox before starting. It never enables full access. Execution supports text and authorized localImage inputs as described below; other resource inputs are rejected. A local queued reservation correlates native start/progress/approval/completion; a validated terminal turn returned by queue/start also establishes terminal state. A start acknowledgement alone is not completion. Failures after start submission mark the reserved turn unknown, preserving reconciliation instead of duplicating work. The authority can change between reads and the native start call; no atomic policy/content revision guarantee or exclusive cross-client scheduling is claimed.

`nativeQueueEvents:true` forwards validated thread/queue/changed from the current RPC generation to a content-free queue.changed invalidation for exact granted session identities. Android refreshes an open queue after these events and connection changes, coalescing events arriving during a request. The queue remains explicitly refreshable for missed events; drafts being edited are retained. This is explicit start, not a background Bridge scheduler or proof that original desktop automatically dispatches every pending entry.

## Native queue attachments

`nativeQueueAttachments:true` permits optional `attachments` on `queue.add`, using the existing bounded `{name,data}` attachment format (4 files, 512 KiB total). Inputs are prepared inside the granted project and sent to the native queue; old text-only requests remain valid. Nonimage files use the existing text path-reference representation. Nontext queue editing remains rejected to preserve attachments.

Queue start permits text and localImage only. Local images must resolve and open inside the exact granted project, be regular files at most 8 MiB, and have a supported PNG/JPEG/GIF/WebP signature. Other resource types are rejected. Validation runs before resume and immediately before local reservation; native path reopening is not atomic with these checks, and no cross-client content revision guarantee is claimed. Android gates attachment queueing and image start on the additive capability. Queue execution uses workspace approval defaults and does not inherit composer mode/model/full-access choices.
